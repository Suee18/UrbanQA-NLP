Implementation

The eight stages, one at a time

Each card below is one module in src/. The "what it does" sections explain what happens at runtime and why the implementation choice was made. Models, file paths, and dependencies are spelled out so you can swap any piece independently.

01
Data Collection already done

Scrapes Wikipedia, NewsAPI, and tourism sections for 20 cities. Each source goes into its own JSON file under data/raw/ tagged with the city name, source type, URL, and a scrape timestamp. Wikipedia + tourism are static; news is a live feed.

src/collection/scraper.py · news_scraper.py · tourism_extractor.py
wikipedia-apirequests BeautifulSoup4NewsAPI
02
Preprocessing & Segmentation already done

Three sub-stages chained together: clean → segment → tokenize. Cleaning strips markup with ftfy/BeautifulSoup. Segmentation uses spaCy's sentencizer, then bundles sentences into 3-sentence overlapping passages with 1-sentence stride — short enough that the QA reader can attend over them, long enough to retain context. Tokenization stores both the raw token list (case + punctuation preserved) and a normalized list (lemmatized, lowercased, stopwords + punct removed) — BM25 uses the normalized list, dense embeddings use the original text.

src/preprocessing/{cleaner, segmenter, tokenizer}.py → data/processed/{city}_passages.json
spaCyftfy BeautifulSoup4
03
Linguistic Analysis (NER + POS) already done

Runs en_core_web_lg over every passage and stores entity tags (PERSON, ORG, GPE, LOC, DATE, CARDINAL, etc.) plus per-token POS + dependency labels. The entity tags get reused four times downstream: (1) the gold QA builder uses them as candidate answer spans; (2) the query processor uses GPE/LOC tags to detect which city a question is about; (3) the answer extractor uses them to validate that "when" answers carry DATE entities; (4) the corpus exploration notebook visualizes the entity distribution per city.

src/analysis/ner_pos.py → 217,933 tagged entities across 20,554 passages
spaCy en_core_web_lg
04
Indexing & Representation built this session

Two indexes built from the same passage list, queryable independently.

BM25 (sparse). Built with rank-bm25 over the normalized tokens. Weights words by inverse document frequency — great at exact keyword matches ("Saladin", "Mamluk") and queries with specific named entities. Stored as a pickle: data/indexes/bm25.pkl (17.4 MB). The pickle includes a parallel "lightweight metadata" list (passage_id, city, source, text only — no heavy entity arrays) so the retriever can hydrate results without re-reading the 20 city files.

FAISS dense (semantic). Each passage text is encoded with sentence-transformers/all-mpnet-base-v2 into a 768-dimensional vector, L2-normalized so inner-product search equals cosine similarity. Stored as a flat IP index: data/indexes/dense.faiss (60.2 MB) plus dense_meta.json with the same metadata list as BM25 (in the same order — so passage indices are comparable across the two indexes, which is what RRF needs). Strong on paraphrases ("how big is Tokyo" → passages saying "Tokyo's population is").

src/indexing/bm25_index.py · dense_index.py
rank-bm25sentence-transformers all-mpnet-base-v2FAISS
05
Query Processing built this session

Runs at QA time on the user's question. Two jobs:

(a) Question-type classification via ordered regex on the first word: what / who / when / where / how_many / how / which / why / other. Each type maps to a list of expected NER labels for the answer span — e.g. "when" expects DATE/TIME, "who" expects PERSON/ORG. That mapping gets reused downstream as a soft post-filter on extracted answers.

(b) City detection. Two-pass strategy. First pass: substring match against a hand-curated alias map covering historical names, abbreviations, and ASCII variants — NYC → New York City, Bombay → Mumbai, Constantinople → Istanbul, Peking → Beijing, Edo → Tokyo, Sao Paulo / São Paulo, etc. Aliases are word-boundary matched so "rome" doesn't fire on "chrome". Longest alias wins so "new york city" beats "new york". Second pass: spaCy NER on the question looking for GPE/LOC/FAC entities, alias-matched again. Output: {detected_city, city_confidence (1.0 substring · 0.7 NER · 0.0 missing)}. The retriever then uses detected_city as a hard filter on candidate passages.

src/retrieval/query_processor.py
spaCy en_core_web_lgregex curated alias map
06
Passage Retrieval built this session

Class Retriever with three modes for the ablation: bm25, dense, hybrid. The expensive resources (BM25 pickle, FAISS index, mpnet encoder, cross-encoder, spaCy) all load lazily — a BM25-only run never pays the cost of loading the cross-encoder.

City filter
Applied before scoring, not after. For BM25 we mask out non-matching passages (set their scores to -inf). For FAISS — which can't filter mid-search — we over-fetch (top_k × 10), then keep only the matching ones. Either way the retriever returns the right city's passages or returns nothing.
Hybrid fusion (RRF)
Reciprocal Rank Fusion from Cormack et al.: score(passage) = Σ 1 / (k + rank_in_list) with k = 60. No need to normalize BM25 scores (raw values, often {1–30}) against dense cosine scores ({0–1}) — RRF only cares about ranks. BM25 and dense indexes were built from the same passage list in the same order, so passage indices are directly comparable.
Cross-encoder rerank
cross-encoder/ms-marco-MiniLM-L-6-v2 scores (question, passage) pairs jointly — much more accurate than cosine since it can attend across the two together. Applied as a final pass over the top-K hybrid candidates. Adds ~200 ms per query and visibly improves rank-1 quality.
src/retrieval/retriever.py · class Retriever
rank-bm25FAISS ms-marco-MiniLM-L-6-v2RRF k=60
07
Answer Extraction built this session

Wraps deepset/roberta-base-squad2 as AnswerExtractor. Loads the model directly via AutoModelForQuestionAnswering + AutoTokenizer (the high-level pipeline("question-answering") API was removed in transformers 5.x).

Multi-passage scoring
Runs the QA model on the top read_k retrieved passages (default 3), picks the highest-confidence non-empty answer. Standard reader-over-retriever pattern: lets the system recover when retrieval got the right city but the wrong best passage at rank 1.
SQuAD 2.0 "no answer"
For each passage we compute scores for every (start, end) token pair (capped at 30 tokens length, top-20 candidates from each axis). The [CLS] token at index 0 represents "no answer here." If the best (CLS, CLS) score beats the best real span, the model emits an empty answer — what we want for irrelevant passages. Confidence is sigmoid(best_span_score − cls_score), so it's bounded [0,1] and tells you "how much more confident than no-answer".
Type validation
For typed questions ("when", "who", "where", "how_many"), we run spaCy NER on the extracted span. If no entity in the span carries an expected label (e.g. "when" expects DATE/TIME), confidence is multiplicatively penalized by 0.5×. Soft penalty, not zero — a strong wrong-type answer can still win over a weak right-type one. Cheap post-filter that catches obvious extraction failures.
src/qa/extractor.py · class AnswerExtractor
deepset/roberta-base-squad2PyTorch spaCy
08
Evaluation & Error Analysis built this session

Three pieces — gold-set generation, metrics, error categorization — all reading and writing JSON so you can inspect any intermediate output.

Gold QA auto-generation
src/evaluation/gold_qa_builder.py. For every passage already NER-tagged, takes typed entities (PERSON, DATE, GPE, CARDINAL, …) as candidate answer spans. Inserts <hl> markers around the span, feeds to valhalla/t5-base-qg-hl, gets back a natural-language question. Filters: span length, blacklist words, dedupe within passage, dedupe within city, answer-leaks-into-question check. Generated 200 balanced candidates (10/city × 20 cities), distributed across 8 question types. Question type is derived from the generated question's first word — not the entity label — so a "When did Saladin..." question about year "1176" (NER-tagged CARDINAL) correctly gets type: when.
Metrics
src/evaluation/metrics.py. Exact Match and token F1 both with SQuAD-style normalization (lowercase, strip articles, strip punctuation, collapse whitespace) — multiple gold answer aliases supported. Recall@1/3/5/10 and MRR computed over questions that include a gold_passage_id. Runs all three retrieval modes and saves per-mode JSON to data/gold_qa/results/{mode}.json. Buckets results by question type and city for slice analysis.
Error categorization
src/evaluation/error_analysis.py. Every wrong prediction (EM = 0) is tagged with the first-matching failure category: CITY_NOT_DETECTED, RETRIEVAL_MISS (gold passage wasn't in top-k), PARTIAL_MATCH (F1 > 0 but EM = 0 — boundary disagreement), or EXTRACTION_FAIL (gold passage was retrieved but extractor returned wrong span). Output is a markdown report per mode: data/gold_qa/analysis/{mode}_analysis.md — ready to drop into the final write-up's analysis section with example failures per category.
src/evaluation/{gold_qa_builder, metrics, error_analysis}.py
valhalla/t5-base-qg-hl SQuAD normalization RRF · MRR · Recall@k
Runtime

What happens when you ask a question

Single entry point: UrbanQA.answer(question) in ask.py. Every UI surface (the CLI, the Streamlit demo, the future Unreal/UDP server) is a thin wrapper over this one call. Below is exactly what happens for a real question end-to-end.

1

Input

The user asks a question. No structure required, no city tag, no question prefix.

"When was Cairo founded?"
2

Query processing

Regex matches "When" → question_type: when → expected entity types [DATE, TIME]. Substring match on "Cairo" against the alias map → detected_city: "Cairo" at confidence 1.0.

{ "question_type": "when", "expected_entity_types": ["DATE", "TIME"], "detected_city": "Cairo", "city_confidence": 1.0 }
3

Retrieval (hybrid, the default)

BM25 and dense each return their top-20 candidates among Cairo's passages only (city filter applied before scoring). RRF fuses the two ranked lists into a single hybrid ranking. The cross-encoder reranks the top-5 with joint (question, passage) attention.

retrieved[0] = { "passage_id": "Cairo_wiki_6", "city": "Cairo", "source": "wikipedia", "score": 0.031, // RRF score post-rerank "text": "Subsequently, Cairo was founded in 969..." }
4

Answer extraction

RoBERTa-squad2 runs on the top-3 retrieved passages. For each, it scores every (start, end) span pair under 30 tokens long and compares against the [CLS]–[CLS] "no answer" baseline. Span "969" wins on Cairo_wiki_6; other passages emit empty.

{ "answer": "969", "raw_confidence": 1.0, "type_match": false, // spaCy tagged "969" as CARDINAL, not DATE "confidence": 0.5 // raw × 0.5 type-mismatch penalty }
5

Unified payload

One JSON-serializable dict combining query analysis + retrieved passages + the chosen answer + every QA candidate considered. This is what every UI surface receives.

{ "question": "When was Cairo founded?", "mode": "hybrid", "answer": "969", "confidence": 0.5, "type_match": false, "query": { /* stage 5 output */ }, "source_passage": { /* the winning passage */ }, "retrieved_passages": [ /* full top-k */ ], "all_candidates": [ /* every QA candidate scored */ ] }
Evaluation results

Hybrid wins, by a lot

Ran all three retrieval modes against the 200-question auto-generated gold set. Hybrid retrieval reduces retrieval misses from 21 (BM25) to 5 — a 76% drop. Every target metric from the original project plan is met or exceeded except MRR, which is 0.568 vs a 0.6 target (close, and rank-1-sensitive).

Methodology caveat to disclose in the report: the gold set was auto-generated from the corpus — every question is grounded in a passage we know exists. This biases numbers upward versus a held-out human-written set. Many "PARTIAL_MATCH" failures are actually cases where the system gave a more correct answer than the gold ("Between 1250 and 1517" vs the auto-truncated gold "Between 1250"). Real EM is likely higher than 76.5%.

Failure categories (hybrid mode)
Partial match · 26 of 47
Answer is close but boundary differs ("12" vs "nearly 12"). Often the system is more correct than the gold — gold answers were extracted by NER and sometimes truncated.
Extraction fail · 16 of 47
Gold passage WAS retrieved (good) but the QA reader picked a wrong span. Often a sibling entity in the same sentence — fixable with stricter type validation or reader fine-tuning.
Retrieval miss · 5 of 47
Gold passage wasn't in the top-5 retrieved — the rare case where even hybrid + rerank missed it. Mostly questions phrased very differently from the source passage.
City not detected · 0
Every question in the gold set referenced its city by name (since it was auto-generated from per-city passages). Real-world questions might fail here.
Unified payload

One JSON shape, three consumers

UrbanQA.answer(question) always returns this exact shape. The CLI prints part of it. The Streamlit demo renders all of it. The future Unreal/UDP server will serialize it as bytes and stream it — no payload reshaping anywhere.

{ "question": "When was Cairo founded?", "mode": "hybrid", // retrieval mode used "query": { // stage 5 — query processor output "question_type": "when", "expected_entity_types": ["DATE", "TIME"], "detected_city": "Cairo", "city_confidence": 1.0 }, "answer": "969", // stage 7 — best answer "confidence": 0.5, // 0..1; includes type-validation penalty "type_match": false, // did span carry an expected NER label "source_passage": { // the passage the answer came from "passage_id": "Cairo_wiki_6", "city": "Cairo", "source": "wikipedia", "text": "Subsequently, Cairo was founded in 969..." }, "retrieved_passages": [ ... ], // stage 6 — full top-k with rank, score, text "all_candidates": [ ... ] // every QA candidate scored across read_k passages }

Designed for the Unreal integration

The whole payload is JSON-serializable strings, numbers, lists, and dicts — no numpy arrays, no torch tensors, no spaCy doc objects. When the UDP/socket.io server gets wrapped around UrbanQA.answer(), it's just json.dumps(payload).encode() on the way out and json.loads(bytes) for the question coming in. The Streamlit demo and Unreal dashboard render the same data; only the transport changes.

Run it now

Three ways to use it today

CLI — single question, pretty-printed
Returns the answer, source passage, confidence, and detected city. Add --mode bm25 or --mode dense for the ablation modes.
python ask.py "When was Cairo founded?"
CLI — JSON output (for piping)
Same payload, machine-readable. This is exactly what the Unreal/UDP server will emit.
python ask.py "Who designed the Sydney Opera House?" --json
Streamlit demo
Browser UI with mode toggle, top-k slider, answer-span highlighting in the source passage, and a raw-JSON expander showing the payload Unreal will consume.
streamlit run app.py → open http://localhost:8501
Re-run the full evaluation
Runs all three modes on the gold set, writes per-mode results JSON + markdown error analysis. Takes ~30 min on CPU.
python src/evaluation/metrics.py && python src/evaluation/error_analysis.py
Generate more gold candidates
Auto-generates question/answer pairs from the corpus using a T5 question-generation model. Pass --per-city N to control quantity.
python src/evaluation/gold_qa_builder.py --per-city 15
What's next (whenever you want)

Three obvious wins

A
Manual cleanup of the gold set (~30 min)

The 200 auto-generated candidates have ~80% directly usable + ~15% needing minor answer-span edits + ~5% to delete. A 30-minute pass through data/gold_qa/gold.jsonl would push hybrid EM from 76.5% → ~85%+ by fixing answer-boundary mismatches like "Between 1250" → "Between 1250 and 1517". For an even more rigorous eval, hand-write 20 "wild" questions phrased differently from any source passage and run them as a held-out split.

B
Unreal Engine integration

Wrap UrbanQA.answer() with a UDP or socket.io server (~1 day). Reads JSON questions from the Unreal client, returns the unified payload as JSON. Because the payload is already fully serializable, this is mostly transport plumbing — no QA-side refactor needed.

C
Stretch: fine-tune on city domain

Use the auto-generated gold set as training data and fine-tune distilbert-base-squad2 on it. Compare against the zero-shot RoBERTa-squad2 baseline. This is one of the artifact's stated stretch goals — would give the report a "supervised vs zero-shot" experiment.
